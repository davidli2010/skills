# 实战经验与踩坑总结

> 以下经验来自实际运行 LLM Wiki 过程中积累的模式和教训，已按 OKF v0.2 约定更新。

---

## 资料获取技巧

- **微信公众号文章无法直接 curl 抓取**（有反爬验证码机制），推荐用 Obsidian Web Clipper 浏览器扩展剪藏为 Markdown，再放入 `raw/` 目录。
- 剪藏后的文件自带 YAML frontmatter（title、source、author、created、tags），可直接利用其中的作者/来源信息填到 `sources[].author`、`sources[].title`。
- 剪藏后立即用快捷键（如 `Ctrl+Shift+D`）下载文章中的图片到本地，避免外链失效。
- LLM 不能一次性读取含内联图片的 Markdown——先读文本，再单独查看引用的图片获取额外上下文。

---

## Assets 使用指南

`raw/assets/` 用于存放原始资料中引用的图片、PDF 附件等二进制文件。以下是完整的使用规范。

### 文件来源

- Obsidian Web Clipper 剪藏后，通过"下载附件"功能自动保存到 `raw/assets/`
- 手动下载的截图、图表、PDF 等也放入此目录
- 用户手动拖入的参考图片

### 命名约定

采用 `来源标识-描述性名称.扩展名` 格式，保证可追溯：

```
raw/assets/
  article-title-fig1-architecture.png
  paper-name-table2.png
  competitor-a-pricing-screenshot-2026q1.png
  manual-sketch-system-design.jpg
```

如果文件由 Obsidian Web Clipper 自动下载，保留其原始文件名即可（通常为 URL hash 或原文件名）。

### 在 wiki 页面中引用

wiki 页面使用**相对路径**引用 assets 中的图片（跨 bundle，从 `wiki/` 目录向上到 `raw/assets/`）：

```markdown
<!-- 从 wiki/ 目录引用 raw/assets/ 中的图片 -->
![架构图](../raw/assets/article-title-fig1-architecture.png)
```

### 摄入时的图片处理流程

LLM 在摄入含图片的资料时，按以下步骤处理：

1. **先读文本内容**，理解整体结构和上下文
2. **逐个查看引用的图片**（如架构图、数据表格截图等），提取额外信息
3. **在摘要页中用文字描述图片关键内容**，同时保留图片引用链接
4. **对于关键图片**（架构图、流程图等），在 wiki 页面中同时保留：
   - 图片引用（供人类阅读）
   - 文字描述（供 LLM 未来查询时无需重新读取图片）

示例：

```markdown
## 系统架构

![系统架构图](../raw/assets/source-article-architecture.png)

> 图片描述：三层架构，前端（React）→ API 网关（Kong）→ 微服务集群（Go），
> 数据层使用 PostgreSQL + Redis。服务间通过 gRPC 通信。
```

### 注意事项

- **LLM 绝不修改 `raw/assets/` 中的文件**——与 `raw/` 的其它内容一样，assets 是不可变的
- **外链图片应尽早本地化**——网络图片 URL 随时可能失效，剪藏后立即下载附件
- **大文件考虑体积**——视频、大型 PDF 等可以只在 wiki 中记录外部链接，不必下载到本地
- **git 管理**——如果仓库中 assets 体积过大，考虑使用 `.gitignore` 排除或使用 Git LFS

## 交叉引用原则

这是维护 wiki 质量的关键，每次摄入和更新时都要遵守：

1. **每个页面底部都要有来源引用**，用 footnote keyed to `sources[].id` 指回来源摘要页，确保可溯源。
2. **新资料导入时主动检查已有页面**是否需要更新——新案例可能补充到已有实体页，而不是只创建新页面。
3. **摘要页末尾列出"相关概念"**，形成概念网络，让知识不是孤岛。
4. **标注跨资料关联**：当多篇资料提到相似观点时，在页面中明确标注（如"与 [相关页面](../concepts/xxx.md) 的共同主题：..."），让 LLM 和人类都能看到知识之间的联系。
5. **链接用相对路径**（如来源摘要页中的 `../entities/xxx.md`），让普通 Markdown 渲染器可打开；移动页面时同步更新链接。

## 知识关联发现

导入第二篇及以后的资料时，重点关注以下四类关联：

| 关联类型 | 说明 | 处理方式 |
|---------|------|---------|
| 共同主题 | 多篇资料反复出现的观点 | 在相关页面中标注，如"与 [xxx](../concepts/xxx.md) 的共同主题：..." |
| 矛盾观点 | 不同资料的冲突论断 | 明确标注矛盾，附带来源和日期，不偷偷覆盖；矛盾应体现在 `sources[]` 与正文 footnote 中 |
| 补充关系 | 新资料为已有概念增加案例/数据 | 更新已有页面，而非只创建新页面 |
| 概念演化 | 同一概念在不同资料中表述不同 | 页面中综合呈现不同侧重，标注出处 |

## 常见导入规模

根据实践，一篇中等长度的文章（2000-3000 字）通常：

| 操作 | 数量 |
|------|------|
| 新建页面 | 2-4 个（1 个来源摘要 + 1-3 个实体/概念） |
| 更新已有页面 | 2-4 个 |
| 总计触及文件 | 5-8 个 |

注意：Karpathy 原文提到"单个来源可能触发 10-15 个页面更新"——这是 wiki 积累到一定规模后的情况。初期 wiki 页面少，关联也少，触及的文件会更少。随着 wiki 成长，每次摄入影响的范围会自然扩大。

## 版本管理建议

- 竞品档案等时效性强的内容，建议在 frontmatter 用 `stale_after` 标注过期日期（OKF §5.5，绝对日期），而不是靠文件名带日期（如 `competitor-a-2026q1.md`）。
- Wiki 页面本身不需要日期后缀——通过 git 历史追踪变化。
- `log.md` 是了解知识库演进的最佳入口，比翻 git log 更直观。
- 建议每次摄入后做一次 git commit，commit message 可直接引用 log.md 的最新条目。

---

## 大文件分块写入

使用 LLM agent 创建 wiki 页面时，单次写入不要超过约 200 行。过大的生成会导致 API 流空闲超时。

**推荐做法**：
1. 先写骨架——frontmatter + 各级标题 + 第一个章节的内容
2. 再用逐次编辑追加剩余章节，每次一个章节
3. 对于特别长的综述或对比分析页，拆分为多个关联页面而非一个巨大文件

这个技巧适用于所有 LLM agent 操作（摄入、查询产出、lint 报告），不仅仅是 wiki 页面创建。

## OKF 相关的常见问题

- **为什么不用 `confidence` 字段？** OKF 记录客观信号（来源、时间、actor），不记录主观评分——评分不可跨消费者移植且会过时。信任由 `verified` 推导出信任层级。
- **为什么正文引用用 footnote 且 label 必须是 `sources[].id`？** 位置索引（`sources[0]`）会在来源列表被 agent 重排时静默错配；稳定的 `id` 重排后依然可靠（OKF §5.1）。
- **为什么 `stale_after` 用绝对日期？** 绝对日期使过期判断是纯日期比较，不依赖"读取时刻"（OKF §5.5）。
